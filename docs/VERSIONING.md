# Версии и выпуски TermTalk

Используем [Semantic Versioning 2.0.0](https://semver.org/lang/ru/).
Версия относится к клиенту, серверу и общим библиотекам как одному проекту.
Источником номера является `project(TermTalk VERSION X.Y.Z ...)` в CMakeLists.txt.
Git-тег выпуска — `vX.Y.Z`; префикс v не входит в сам номер SemVer.

## Что считаем публичным интерфейсом

- Типы, функции и контракты публичных заголовков libs/*.h.
- Аргументы запуска и документированное поведение клиента и сервера.
- Реально реализованный формат обмена и его совместимость между клиентом и сервером.

WSCK v1 реализован в 0.4.0; текущий WSCK v2 из PROTOCOL.md — в 0.6.0; предложенные будущие расширения
не считаются уже реализованным интерфейсом. Версия приложения и поле версии
сетевого протокола независимы:
изменение номера приложения само по себе не меняет формат обмена.

## Выбор номера

Формат — MAJOR.MINOR.PATCH. После повышения MINOR сбрасываем PATCH;
после повышения MAJOR сбрасываем MINOR и PATCH.

Пока MAJOR равен 0, проект находится в начальной разработке, API нестабилен.
Для этого периода принимаем соглашение:

- Новые возможности или несовместимый контракт: 0.2.0 → 0.3.0.
- Совместимые исправления: 0.2.0 → 0.2.1.
- Документация и внутренние изменения без изменения поведения могут получать
  обычные коммиты без отдельного выпуска; если нужен самостоятельный выпуск
  обслуживания, повышаем PATCH.

С версии 1.0.0 несовместимый публичный интерфейс требует повышения MAJOR,
совместимые возможности — MINOR, совместимые исправления — PATCH.
Переход к 1.0.0 требует отдельного решения о стабильности API и составе продукта;
ранний выпуск 0.x не означает готовность полного ТЗ или закрытие всех задач roadmap.

При необходимости используем предрелизные номера, например 0.3.0-alpha.1.
CMake project(VERSION) хранит числовую основу; поддержку суффикса в настройках
сборки нужно добавить перед первым таким выпуском. Пока выпускаем числовые X.Y.Z.

## Порядок выпуска в Git

1. Отобрать относящиеся к выпуску изменения; пользовательские эксперименты и
   результаты сборки не включать автоматически. Проверить рабочие и staged diff.
2. Обновить номер в CMakeLists.txt, CHANGELOG.md, затронутую документацию и roadmap.
   В журнале явно описать несовместимость и необходимые действия по переходу.
3. Собрать клиент и сервер, выполнить относящиеся проверки. Зафиксировать границы
   проверки; тесты не подтверждают ещё не реализованные возможности.
4. Сделать тематические коммиты и коммит выпуска. Создать аннотированный тег
   vX.Y.Z на проверенном коммите, указав состав и проверку в аннотации.
5. Проверить номер, коммит тега и состав выпуска. Не перемещать и не переиспользовать
   выпущенный тег: исправления выходят под новым номером.

Пользователь поручил вести выпуски: локальные коммиты и теги в рамках согласованных
изменений не требуют повторного согласования. Создание версии не означает push,
публикацию GitHub Release или упаковку бинарных файлов. Эти действия выполняются
отдельно по поручению. Перед первой отправкой согласуем состав публичной истории.

## Начало истории версий

До введения этого правила CMake содержал 0.1.0, но соответствующего тега не было.
Не создаём задним числом выпуск без отдельной проверки исторического состояния.
Первый помеченный выпуск — 0.2.0 с изменениями NET-01 и документацией API.

## Публичная история GitHub

Репозиторий https://github.com/Techell/TermTalk создан с MIT-лицензией.
Публичная main продолжает этот начальный коммит единственным чистым импортом
готового проекта. Предыдущая история разработки и теги v0.2.0–v0.9.0 сохранены
локально; их не отправляем автоматически и не переносим на другие коммиты.
Версия приложения при импорте остаётся 0.9.0. Добавление лицензии и документов
не объявляет новый функциональный выпуск. Следующие выпуски получат новые
аннотированные теги на проверенных коммитах публичной ветки.
