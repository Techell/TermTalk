# SEC-01: модели угроз и план изучения

Дата исследования: 2026-10-21. **Предложение для обсуждения**, модель ещё не
выбрана. В 0.8.0 нет TLS, E2EE и шифрования локальной истории. Этот документ
не является спецификацией уже реализованного протокола.

## 1. Что защищаем и от кого

Активы: тексты, содержимое/имена файлов, ключи личности, история на диске,
подлинность собеседника и целостность сообщений. Никнейм и серверный ID не
доказывают личность. SHA-256 файла сейчас обнаруживает несовпадение содержимого,
но сервер, способный менять файл и его ожидаемый хеш, не аутентифицируется.

| Модель | Противник и доверие | Необходимая защита | Остаточная видимость |
| --- | --- | --- | --- |
| A. Доверенный сервер | Сеть может читать, менять, повторять трафик и подменять сервер | Аутентифицированный TLS, проверка сертификата/закреплённого ключа, без отката к открытому каналу | Сервер читает сообщения и файлы |
| B. Недоверенный сервер | Дополнительно сервер может подменять маршруты и ключи, хранить трафик | E2EE клиентов, независимые ключи личности, проверка отпечатка вне сервера, политика смены ключа; TLS снаружи | Сервер видит IP, маршруты, размеры и время, может блокировать доставку |
| C. Компрометация ключей во времени | Сохранённый трафик, временное похищение состояния, будущий квантовый противник | Forward secrecy, восстановление защиты после компрометации, гибридные постквантовые механизмы; отдельно офлайн/несколько устройств | Не скрывает метаданные и не спасает активно заражённый клиент |

Предлагаю B как целевую модель личного чата, A как первый проверяемый этап.
Для двух одновременно подключённых клиентов можно изучить опубликованный
[Noise XX](https://noiseprotocol.org/noise.html), включая привязку постоянного
ключа к личности. Схема первого доверия TOFU не исключает атаку при первом
контакте; нужен сравниваемый отпечаток/QR и явное решение при смене ключа.
Постоянный обмен ключами, хранение идентичности и миграция протокола требуют
отдельного согласованного контракта. Комбинация отдельных примитивов сама по
себе не образует проверенный протокол.

Заражённые конечные устройства, копирование получателем, анонимность маршрутов
и полная доступность вне обещаний этих моделей. Ограничения ресурсов и защита
от DoS нужны независимо. Текущая WSH1 хранит открытый текст: E2EE канала этого
не исправляет; защита локальных ключей/истории — отдельная задача.

## 2. Алгоритмы: разные задачи, разные инструменты

| Роль | Кандидаты для изучения |
| --- | --- |
| Аутентифицированное шифрование, AEAD | AES-256-GCM или [ChaCha20-Poly1305, RFC 8439](https://www.rfc-editor.org/rfc/rfc8439.html), включая контрольные примеры |
| Обмен общим секретом | X25519, ECDH P-256; аутентификация обмена обязательна |
| Подпись личности, если требует выбранный протокол | Ed25519 или ECDSA P-256; подпись не шифрует сообщение |
| Разделение и получение ключей | HKDF-SHA-256, HMAC; отдельные ключи по направлениям и назначению |
| Постквантовое установление секрета | [ML-KEM, FIPS 203](https://csrc.nist.gov/pubs/fips/203/final), в опубликованной гибридной схеме |

ML-KEM — механизм инкапсуляции ключа, не замена AEAD для текста/32-ГиБ файла.
Kyber и стандартизованный ML-KEM нельзя считать произвольно взаимозаменяемыми
реализациями. Случайность должна поступать из системного криптографического
генератора, а не rand/time. Поддержку примитивов выбранным Windows-провайдером
нужно проверить на всей матрице ОС.

Для AEAD нельзя повторять nonce с одним ключом: нужны счётчики/эпохи, разделение
направлений, пределы и безопасное поведение после сбоя. Проверять тег до выдачи
открытого текста приложению. Аутентифицировать контекст: версию, сеанс,
направление, участников, номер сообщения; у файла ещё transfer ID, блок,
смещение, размер и завершение. Запретить повторы, перестановку и склейку сеансов.
Текущий request ID — корреляция запросов, не криптографическая защита от повтора.

## 3. Что опубликовано у современных мессенджеров

| Продукт | Опубликованный подход |
| --- | --- |
| Signal | [PQXDH](https://signal.org/docs/specifications/pqxdh/) для начала сеанса; [Double Ratchet](https://signal.org/docs/specifications/doubleratchet/). В 2025 [анонсированы SPQR и Triple Ratchet](https://signal.org/blog/spqr/); не утверждаем завершённость развёртывания на всех клиентах |
| WhatsApp | [Signal Protocol для личных сообщений/звонков](https://www.whatsapp.com/privacyquestions); это не подтверждает наличие всех новых расширений Signal |
| iMessage | [PQ3](https://security.apple.com/blog/imessage-pq3/): гибрид ECDH P-256/Kyber и периодическое обновление ключей, AES-256-CTR с ECDSA-подписью сообщений |
| Telegram | [Облачные чаты и Secret Chats различаются](https://telegram.org/faq#q-how-do-you-encrypt-data): сквозное шифрование только у Secret Chats; [MTProto 2.0](https://core.telegram.org/api/end-to-end) использует AES-256-IGE |

Не копировать один режим AES из таблицы в новый протокол: безопасность зависит
от всей схемы, проверки подлинности и состояния. Стандарты и обновления продукта
не означают одинаковую реализацию во всех клиентах/версиях/режимах.

## 4. Учебный план и проверяемые результаты

1. Зафиксировать модель A/B/C, доверие, регистрацию ключа, первый контакт,
   смену ключа, поддержку офлайн и нескольких устройств. Результат — контракт,
   диаграмма обмена и негативные сценарии, включая злонамеренный сервер.
2. Изучить CSPRNG, байтовые форматы, SHA-256/HMAC/HKDF. Учебные реализации
   изолировать от рабочего чата и проверять опубликованными векторами.
3. AEAD: векторы, пустые/граничные сообщения, порча ciphertext/tag/AAD,
   неверный ключ, повтор nonce, ограничение длины. Ошибка не выдаёт plaintext.
4. Аутентифицированный обмен: разобрать Noise XX и Signal, сравнить MITM,
   отпечатки, эфемерные/постоянные ключи, удаление старых секретов. Не проектировать
   собственную схему обмена из отдельных изученных формул.
5. Транспорт: [TLS 1.3, RFC 8446](https://www.rfc-editor.org/rfc/rfc8446.html),
   проверка цепочки/имени либо явная модель закрепления ключа, отрицательные тесты,
   частичные операции, закрытие, отсутствие plaintext fallback. У системного
   [Schannel TLS 1.3 начинается с Windows 11 / Server 2022](https://learn.microsoft.com/en-us/windows/win32/secauthn/protocols-in-tls-ssl--schannel-ssp-).
   Для сохраняемой Windows 10 отдельно выбрать TLS 1.2 с ECDHE+AEAD или библиотеку
   TLS 1.3; не обещать TLS 1.3 через Schannel на Windows 10.
6. E2EE личного сеанса/файлов: отдельные CryptoProvider, PeerSession, KeyStore,
   TlsStream. UI не управляет криптографическим состоянием. Проверить изменение,
   повтор, обрыв, переподключение, чужой ключ, файл без финального блока и
   серверную квоту с учётом накладных расходов шифрования.
7. Ratchet: разграничить защиту прошлых ключей и восстановление будущей защиты
   после временного взлома. Проверить атомарную запись состояния, откат после
   сбоя, повтор сообщений, предел пропущенных ключей и безопасное удаление.
8. Затем офлайн/prekeys, несколько устройств, гибрид ML-KEM. Для групп отдельно
   изучить [MLS, RFC 9420](https://www.rfc-editor.org/rfc/rfc9420.html), не расширять
   самодельно личную схему до группы.

Согласованное желание писать алгоритмы самостоятельно сохраняем как учебный
трек. Предлагаю отдельно решить, будет ли рабочий чат использовать системный/
проверенный провайдер или экспериментальную реализацию. Успешные векторы и
тесты не заменяют независимый анализ и не дают основания обещать промышленную
безопасность. Реализация SEC-02/SEC-03 в этот выпуск не входит.
